Decisions locked (from our Q&A)

1 · Scope

Everything, phased — 6 waves with a review gate after each.

2 · Canonical name

Model B. Every “Plan B” occurrence renamed.

3 · Per-stack artifacts

Generated from templates + per-stack parameter files kept in this repo.

4 · Lagging clients

Build vscode-crucible.py; extend arduino-crucible.py.

5 · AXI envelope

Upgrade clients to emit the TOON-AXI envelope the crucible skill already promises.

6 · MCP holdouts

sandesh / lean-ctx / mail: docs + AXI CLI contract only; rewrites live in their own repos.

7 · Legacy files

Archive into this repo (archive/ + mapping), then delete via chezmoi.

8 · Big references

Deep reference docs stay in memory/; skills hold procedure and route to them.

9 · Containment rule

Language references are NOT skills. Skill descriptions leak into every session of every project; stack refs load only via stack-scoped skills / project CLAUDE.md.

10 · Core file

CLAUDE.md is always a symlink to AGENTS.md. One frugal core serves both entrypoints; the sub-agent procedure moves to model-b references.

11 · Crucible V2 API

bun-crucible.py is the reference implementation. Plan/cycle verbs are universal V2 API; every stack client adopts the same API + AXI standards. worktree-flow.py migrates to AXI too.

Open questions — annotate to decide

Q1 · Installation config — the seam contract

Proposal: $MODELB_HOME/install.toml — harnesses=[…], version, asset_root. Scaffold resolves it via $MODELB_HOME → package data → repo fallback; --harnesses demoted to a dev-only override. Define the schema NOW (contract or PRD §D10 amendment) so 013 codes against it before 014 ships the installer. The harness set recorded here is also what 014 passes down when invoking Crucible's installer (#1330).

Q2 · Harness selection UX at install

Installer DETECTS installed harnesses (probe claude/codex/gemini/cursor-agent/copilot/opencode/amp binaries) and proposes; user confirms/edits; non-interactive --harnesses flag for CI. Per-harness support stays a FEATURE — installable independently, re-runnable to add one later.

Q3 · Agents under which feature?

The 16 generated agents + generator are Claude-Code-shaped today (~/.claude/agents/). Options: (a) deploy under the Claude harness feature, generator assets shipped and rendered at install; (b) pre-rendered in the package. Other harnesses gain agent equivalents only when their feature defines them. Leaning (a) — keeps build.py --check as the live drift gate.

Q4 · Sequencing 013 ↔ 014

013 stays first (scaffold, dev-mode asset root + config fallback), 014 follows (packaging + installer honoring the same config schema)? Or swap so the installer exists first? Leaning: keep 013 → 014 with Q1's schema fixed up front; dogfood machine keeps chezmoi as its deployment channel, fresh machines use the installer. New input (#1330): 014 additionally invokes Crucible's installer, and client bundling waits on CR-CRU-036's final contract — 013-first got stronger.

Q5 · Upgrade story

Installer re-run = idempotent upgrade: refresh user-local files for the recorded harness set, preserve user edits? (Policy needed: overwrite-managed vs three-way merge vs chezmoi-style source of truth per machine.) Scaffolded projects are NOT touched by upgrades — project files evolve via their own CRs.

Q6 · Skill freeze ↔ installed skills

Confirm: skills deploy ONCE user-scope by the installer; the scaffold's AGENTS.md skill-freeze only REFERENCES them per stack — no per-project skill copies ever. A project targeting a stack whose skills aren't installed ⇒ scaffold warns (installer re-run needed), never emits its own copy.
