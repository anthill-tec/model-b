## Context

A stack's agents are pointed at reference material in `docs/memory/` templates: `rust.toml` cites the
`rust-orchestration` template, and the quarkus agents the Java references (CR-MDB-086). CR-MDB-060
retires `docs/memory/`. A Pi skill gives agent-facing material a home its readers load: only its name
and description reach the prompt, its `SKILL.md` is read when a task matches, and its `references/`
when `SKILL.md` points to them. A skill rendered into a project's `.agents/skills/` reaches only that
project's sessions, and a sub-agent's catalogue, built from its own directory, includes it; a worktree
child finds the tracked copy in its worktree. A definition already tells its agent which skills to
load: a role's `skills` list in the stack file renders as the body line "Load these skills first: …".

This CR builds the mechanism and moves rust's and arduino's agent-facing material. The Java stack
skill's content is CR-MDB-086.

## §S1 — The mechanism

1. **Sources.** A stack skill's source is `generator/skills/<name>/`, the directory named as its
   frontmatter `name`: a `SKILL.md`, and a `references/` directory only when the skill has references.
   `generator/` ships in the wheel; the installer deploys nothing from it. Sources resolve through the
   same asset-root chain as the agent sources (packaged first, then the repository). A source whose
   `SKILL.md` frontmatter `name` differs from its directory is refused before any write, by `init` and
   by `modelb-axi agents`.
2. **The declaration** is one file, `generator/stack-skills.toml`, outside `generator/stacks/`: one
   `[skills.<name>]` table per skill, its `stacks = ["<stack>", …]` naming the stacks it renders for. A stack with or without a stack file may be named (CR-MDB-086
   names `java`, which has none). This CR declares `rust-stack` for `rust`. A declared skill whose
   source has no `SKILL.md` renders nothing.
3. **Rendering.** `modelb-axi init` renders the declared skill of each stack in `--stacks` into
   `.agents/skills/<name>/` at the project root, never in a sub-project, wherever it renders the Pi
   agent definitions, under their ownership rules:
   - `SKILL.md` carries `# generated by modelb-axi (Model B stack skills); sha256 <hash>` inside its
     frontmatter;
   - each reference carries `<!-- generated by modelb-axi (Model B stack skills); sha256 <hash> -->`
     as its first line, read by the first-line ownership form, which takes a suffix after the hash;
   - a hand-modified file is skipped and reported; an unmarked file is never written;
   - `--dry-run` writes nothing; every written file joins `init`'s list of emitted files (its envelope
     and its optional commit); the rendered files are tracked, so every worktree carries them.
4. **Re-rendering.** `modelb-axi agents`, run from the project root as today, re-renders the stack
   skills with the agent definitions, by the same rules, and reports them in its envelope; its "nothing
   rendered" warning stays true only when nothing was written. A re-render writes and never deletes: a
   skill for a stack the project no longer lists stays where it is.
5. **The project's `AGENTS.md`.** Its rendered stack line names a stack's skill only where one is
   declared and rendered: a declared skill whose source has no `SKILL.md` is left off it, as is any
   stack without a declared skill. Both trust surfaces — the
   untrusted-project warning `init` prints and the rendered `AGENTS.md`'s project-trust line — name the
   stack skills among what an untrusted project does not load.

## §S2 — The definitions load it

Every role of the `rust` stack lists `rust-stack` in its `skills`, so each definition's body line
names it, e.g. "Load these skills first: crucible, rust-stack." `rust.toml`'s "Companion memory"
bullet names `rust-stack` instead of the template. `SKILL.md` restates nothing `rust.toml` states;
references move verbatim, apart from the rewordings §S5 requires.

## §S3 — rust and arduino: every agent-facing section leaves its template

An agent-facing section goes to the stack skill when only some tasks need it, into the stack file
when every phase needs it (only the part the stack file does not already state), or is deleted when
the stack file already states all of it. Orchestrator-facing sections stay for CR-MDB-060. Each row
names an anchor phrase, by which its move is checked.

1. **`rust-orchestration.md` to `rust-stack`:**

   | Moves | Anchor | To |
   |---|---|---|
   | "E2E / docker / nextest-concurrency gotchas" | `Container UID owns bind-mount writes` | `references/e2e-docker-nextest.md` |
   | The "Pre-merge gate" bullet on a new docker-dependent test | `added to BOTH nextest default-filters` | `references/e2e-docker-nextest.md` |
   | "Flaky-test investigation principle" (the principle) | `Logical sequence + data integrity preserved` | `SKILL.md` |

   Its "Gate sizing follow-on" paragraph stays in the template under a heading of its own.

2. **`rust-orchestration.md` § "RED/GREEN/VERIFY additions" to `rust.toml`, by role:**

   | Bullet | Anchor | Roles |
   |---|---|---|
   | Clippy runs with `--tests` | `clippy --crate <c> --tests` | the GREEN, VERIFY and FIX clippy commands pass `--tests` |
   | Read the summary, never the exit code | `never the exit code` | GREEN, VERIFY, FIX |
   | `#[ignore]` is temporary | `never a resting state` | RED, GREEN |
   | GREEN may promote a dependency | `from dev-only to production` | GREEN, reconciled with the forbidden-dependency escalation: promoting an existing dev-dependency the code imports needs none; a new or forbidden dependency still escalates |

4. **Stays in `rust-orchestration.md`:** the preamble, "Tooling", "Use the CLI", the `worktree-flow.py`

5. **`arduino-orchestration.md`:** "Hardware drivers" (anchors `Verify the exact part`, `Hardware

   agents" stays; the preamble no longer names gating hardware drivers. No `arduino-stack` skill is
   declared.
6. `rust.toml` names no template path, its provenance header comment included.

## §S4 — Text that stays points at where material went

Every sentence left in a template that names a moved section names its new home. A template names the
stack's agent definitions or its stack skill, never a `generator/stacks/` path (the memory templates
name no generator path).

## §S5 — Rewordings the move requires

1. **The test-run rule (§D21):** no stack skill teaches a runner invocation. A form the raw-runner
   guard's rules match that an agent runs becomes the stack client's verb; a descriptive or checklist
   form is reworded or dropped.
2. **No project named (§D25):** the moved examples name no project's components — `ensure_compose_up`,
   `http_client`, `e2e_kafka`, `e2e_telemetry` and `total_acked` become neutral examples.
3. A stack skill names no `ctx_*` or lean-ctx tool, because it is not rendered in a built-in form as
   the definitions are.

## §S6 — The guards, the gates and the docs

1. **Gates whose roots gain `generator/skills/`:** the raw-runner guard, the AXI envelope guard, the
   skill-frontmatter checks and the Pi skill-loader check (no diagnostics, one skill per directory,
   name and description within Pi's limits, no name shared with a `skills-src/` bundle), the shipped
   text gates `test_tooling_detachment`, `test_deployed_script_invocation`,
   `test_project_registry_schema`, `test_worktree_flow_surfaces` and `test_board_holds_the_queue`,
   `test_cite_by_symbol`'s guarded directories and `test_gap_analysis_reach_and_pre_review`'s ordering
   surfaces.
2. **The orchestrator-rule triage stays frozen.** `test_orchestrator_rule_triage` gains a moved-rules
   map beside its CR-MDB-044 rename map: each frozen row whose rule this CR moves — 191, 192, 211, 284,
   373 and 384 — names its new file and its anchor phrase (§S3), and the gate checks for the phrase there
   instead of checking the old heading and its class rule. The rename map keeps its one entry;
   `audits/2026-09-26-orchestrator-rule-triage.md` is not edited.
3. **Tests repointed** to the moved text: `test_orchestrator_rule_triage`'s check of the arduino
   template's "Hardware drivers" heading and its `HeadingRenameMapTest`; `test_rust_stack_generator`'s
   reads of `rust-orchestration.md`; `test_project_registry_schema`'s stack-line golden; the
   regenerated rust and arduino definitions under `generator/agents/`.
4. `AGENTS.md` § Key Directories names `generator/skills/` and `generator/stack-skills.toml`, and its
   `generator/` row states the stack files and the number of generated definitions the tree holds.

## Acceptance criteria

- [ ] **AC1 (§S1.1–3).** `generator/skills/` holds exactly the skills `generator/stack-skills.toml`
      declares, each in a directory named as its `SKILL.md`'s frontmatter `name`; this CR declares
      `rust-stack` for `rust`, with `references/e2e-docker-nextest.md`. `init` (sandboxed) writes
      `.agents/skills/<name>/` only for the stacks in `--stacks` that declare a skill — for
      `--stacks rust`, `rust-stack` with the frontmatter marker in `SKILL.md` and the first-line marker
      in its reference; `--dry-run` writes nothing; the written files are in `init`'s emitted list; a
      hand-modified rendered file is skipped and reported, and an unmarked file at a rendered path is
      left untouched, by both `init` and `modelb-axi agents`. A fixture declaring a skill for a stack
